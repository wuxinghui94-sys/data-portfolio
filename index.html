三、数据质量治理与 MySQL 独立核验实战（4 类真实排错）

结合 AI 提效的同时，坚持通过 SQL 独立校验、边界测试与人工复核卡点守住数据准确性底线
口径治理 · 财务对账

问题背景与排查思路

痛点现象：月初核算业绩时，销售填报的成交额、CRM 导出的订单表、财务实收流水三方金额存在差额。

根因定位：销售按“下单时间”归属当月，财务按“到账时间”入账，且跨月退费冲销口径未拉齐。

解决与固化：通过 MySQL 关联订单表与财务流水表逐单输出差额明细，推动三方统一“实收归属期 + 跨月退费冲销规则”，写入指标口径文档并固化到核对脚本。

MySQL 跨系统订单 vs 财务流水对账核验示例
SELECT
  COALESCE(o.order_id, f.order_id) AS order_id,
  o.pay_amount AS crm_amount,
  f.settled_amount AS finance_amount,
  (COALESCE(o.pay_amount,0) - COALESCE(f.settled_amount,0)) AS diff_amt,
  CASE
    WHEN o.order_id IS NULL THEN '财务多单/CRM缺失'
    WHEN f.order_id IS NULL THEN 'CRM未到账/跨期'
    WHEN o.pay_amount <> f.settled_amount THEN '部分退款/金额不一致'
  END AS anomaly_type
FROM crm_orders o
LEFT JOIN finance_flows f ON o.order_id = f.order_id
WHERE o.pay_amount <> COALESCE(f.settled_amount, 0);
数据清洗 · 窗口函数去重

问题背景与排查思路

痛点现象：直接对 CRM 流水表 COUNT(*) 统计转化单数与线索数时，部分渠道转化率虚高。

根因定位：同一客户在不同时间重复留资，或高客单课程采用“定金 + 尾款”两笔支付导致单客户拆出 2 条订单记录。

解决与固化：建立以 user_uid + cohort_id 为粒度的主键去重逻辑，使用窗口函数识别首次有效进粉并合并同单定金/尾款实付金额，还原真实唯一成交人数。

MySQL 窗口函数主键去重 & 分笔付款合并示例
WITH dedup_leads AS (
  SELECT user_uid, cohort_id, channel_name, lead_time,
    ROW_NUMBER() OVER (
      PARTITION BY user_uid, cohort_id ORDER BY lead_time ASC
    ) AS rn
  FROM raw_crm_leads
),
merged_orders AS (
  SELECT user_uid, cohort_id, SUM(pay_amount) AS net_paid
  FROM raw_orders WHERE order_status = 'PAID'
  GROUP BY user_uid, cohort_id
)
SELECT l.channel_name, COUNT(l.user_uid) AS unique_leads,
  COUNT(CASE WHEN o.net_paid >= 1980 THEN 1 END) AS valid_orders
FROM dedup_leads l
LEFT JOIN merged_orders o ON l.user_uid = o.user_uid AND l.cohort_id = o.cohort_id
WHERE l.rn = 1 GROUP BY l.channel_name;
质量巡检 · 业务录入规范

问题背景与排查思路

痛点现象：自动化拉取飞书与 CRM 接口后，个别日期线索数骤降或渠道归因中出现大量“未知/空值”。

根因定位：排查发现系 API 分页拉取边界漏数，以及部分一线销售手工录入渠道来源、归属人字段不规范（空格、简称混用）。

解决与固化：在采集脚本中补齐分页游标校验与枚举值映射表，同时每日跑一次 MySQL 空值/脏字段巡检，推动业务端将自由文本改为下拉规范选项。

MySQL 接口完整性与脏字段每日巡检示例
SELECT
  DATE(create_time) AS dt,
  COUNT(*) AS total_rows,
  SUM(CASE WHEN channel_name IS NULL OR TRIM(channel_name)='' THEN 1 ELSE 0 END) AS null_channel_cnt,
  SUM(CASE WHEN owner_id IS NULL THEN 1 ELSE 0 END) AS null_owner_cnt,
  SUM(CASE WHEN channel_name NOT IN (SELECT valid_channel FROM dim_channel) THEN 1 ELSE 0 END) AS invalid_enum_cnt
FROM stg_crm_leads
WHERE create_time >= CURDATE() - INTERVAL 7 DAY
GROUP BY DATE(create_time)
ORDER BY dt DESC;
AI 产出核验 · Human-in-the-Loop

问题背景与排查思路

痛点现象：用 AI 辅助生成 Python 脚本处理 20+ 张日报及月度阶梯提成时，AI 极易在“阶梯临界点（> vs >=）”或“退费扣减顺序”上写出隐蔽 Bug。

核验机制（三层防线）：

1. MySQL 反向独立校验：独立手写 SQL 核对总单量、总金额及临界点员工提成；
2. 抽样回源比对：随机抽取明细与 CRM/财务原流水逐笔核对；
3. 保留人工发布卡点：日均耗时从 3h 压到 0.5h，刻意将最后 0.5h 留作人工复核验收，确保对业务与财务 0 差错交付。

MySQL 月度阶梯提成边界独立校验示例
WITH sales_net AS (
  SELECT owner_id,
    SUM(CASE WHEN is_refund = 0 THEN pay_amount ELSE 0 END)
    - SUM(CASE WHEN is_refund = 1 THEN refund_amount ELSE 0 END) AS net_gmv
  FROM monthly_settled_orders
  WHERE settle_month = '202X-10'
  GROUP BY owner_id
)
SELECT owner_id, net_gmv,
  CASE
    WHEN net_gmv >= 120000 THEN ROUND(net_gmv * 0.08, 2)
    WHEN net_gmv >= 80000 THEN ROUND(net_gmv * 0.06, 2)
    ELSE ROUND(net_gmv * 0.04, 2)
  END AS sql_verified_commission
FROM sales_net ORDER BY net_gmv DESC;
